A Bug the Radio Never Admitted

Done
Open: betaflight-tx-lua-scripts#548 · two lines · these Lua scripts let a pilot tune a quad from the radio transmitter instead of a laptop.
The bug
The Receiver page reads the RC Smoothing on/off setting from byte 25 of an MSP message. Since firmware API 1.44 the flight controller writes a hardcoded zero into that byte and discards it again on write. The real setting lives at byte 32. The ON/OFF labels were inverted on top of that.

So on every Betaflight 4.3 and newer quad, since 2021, the radio showed the wrong state, and toggling it and saving was a silent no-op that reverted on the next read.
My first byte count was wrong
I counted offsets in the firmware's C source and took both branches of every #ifdef and #else, which inflated every offset after the first conditional. Redoing it properly put the setting at byte 32.

The check that actually convinced me was not my arithmetic. It was that six other fields on that same page, stick endpoints, camera angle, the cutoffs, all land exactly where the corrected layout predicts. Only the one field misses.
Then I stopped counting and asked the firmware
Betaflight has a SITL target that compiles the real firmware as a program you can run on a laptop, speaking real MSP over TCP. So I ran it and did exactly what the save path does: change one byte, write it back, read it again, and see which bytes the flight controller actually kept.
MSP over TCP 5761
TEST 1  byte 25, the byte the radio's script writes
  wrote byte 25: 0 -> 1
  bytes that actually changed in the FC: NONE
  firmware kept it?  NO  (discarded)

TEST 2  byte 32, the byte the fix writes
  wrote byte 32: 1 -> 0
  bytes that actually changed in the FC: [32]
  firmware kept it?  YES
That is not an argument about C. That is the firmware answering for itself.
And then the radio itself
EdgeTX, the radio firmware, publishes a WebAssembly build that runs the real thing in a browser. Uploading the scripts and driving the menus showed the bug as a pilot sees it: a toggle reading OFF against a flight controller that has the setting ON, and a save that reverts.

One nuance only the simulator could have revealed, and it changed what I wrote in the pull request: on colour radios the field renders as a toggle built from the raw value, so the inverted labels never show there. That half of the bug is visible only on the older monochrome radios. Without running it I would have overstated the fix.

A Memory-Safety Fix, Merged

Merged
Merged: 3b459d07 into dev, 17 September 2026 · JustVugg/colibri, 33,519 stars · six lines of logic · merged in under 48 hours, no changes requested.
What colibri is, and why I looked there
It runs very large mixture-of-experts language models on ordinary hardware, in plain C with no dependencies, by streaming expert weights off disk. It went from nothing to 33.5k stars in about three months. That combination is exactly what is worth searching: enormous attention, a young codebase, performance-critical C.
The bug
The server reads exactly the number of bytes a client advertises into a buffer of that size, then hands them to the tokenizer as prompt text. Nothing in between checks the bytes are valid UTF-8.

If the prompt ends halfway through a character, a clipped emoji, a cut-off Arabic letter, the decoder still reports that character's full length even though the remaining bytes were never sent. The tokenizer walks past the end of the buffer.

Without a sanitizer it does not crash. It reads whatever sits next in memory, turns it into tokens, and feeds the model a prompt containing bytes the user never sent, with no sign anything went wrong.
Why it was easy to argue
The project had already solved it. The same engine exists twice in that repository, and the other copy carries the bounds check, plus a test gating exactly this case under the maintainer's own comment about byte-counted payloads ending mid-character.

So the pull request was not “I think you have a bug”. It was “your own test fails against your other engine”, and the fix is that copy ported verbatim.

The process detail worth keeping
The commit was about to go out under my university email address, which is not verified on my GitHub account. It would have landed showing an unlinked author and counted for nothing. I caught it by comparing against the address on an earlier merged commit.

Git configuration is per-clone, and it can quietly cost you the credit for your own work.

Measuring Where a Contribution Is Worth Sending

Corrected
Star count says nothing about whether a project will take your work. I wanted a number for how often each candidate actually merges code from people outside the team.
I got it badly wrong the first time
My method was GitHub's author_association field, which labels a pull request's author as a member, an owner, or an outside contributor. On that basis one project looked extraordinary: ninety-four of ninety-four merged pull requests from outside contributors, merging in a median of one hour.

That statistic is false. author_association reports everyone as a plain contributor when an organisation hides its membership list, and this one does. Counting properly, by whether the branch lived in the repository or in a fork, eighty-six of those ninety-four were two employees merging their own branches. Real outside contributions: eight. Across the project's entire history, not one pull request from a fork has ever received a written review.
share of merges from forks
colibri                       49%
VoiceStudio                   29%
PX4-Autopilot                 25%
the one that looked perfect    9%   <- reported as 100%
What I actually take from that
The lesson is not about that project. It is that I presented a number before I understood what it measured, and the number happened to flatter the conclusion I was already leaning toward.

The fix is the same discipline as everywhere else this month: find a second, independent way to measure the same thing, and check whether the two agree.
And a deliberately small fix to PX4
PX4 is the drone autopilot next door to Betaflight. A u-blox GPS parameter declares six configuration bits, so its range is 0 to 63, but it advertises a maximum of 32, the value of the top bit on its own. One line.

My first draft claimed it blocked a valid configuration. Checking showed PX4 never compiles parameter ranges into the firmware at all, so nothing is blocked and the real effect is a wrong bound shown to operators. The pull request says that, not the louder version.

PX4 also requires that any AI assistance be disclosed in the commit, and states plainly that “the AI wrote it” is never an acceptable answer in review. That is the right bar, and one I want to be held to.
