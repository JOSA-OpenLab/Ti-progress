The Standard

The unifying principle: don't optimize on gut feeling. Measure first, fix what actually costs the most (how often it runs times how slow it is), then measure again. Knuth's 97% of code doesn't matter for speed; the whole week is about finding the 3% that does.
Reading a flame graph
  • Width = CPU time, height = call depth. The x-axis is not time; it is how often a function showed up while the profiler sampled.
  • Wide block at the top of a stack. The function actually doing the work. Prime suspect, optimize it directly.
  • Stack stays wide then suddenly narrows. The time went where the width drops, not at the top of the stack.
  • Skinny sliver going way up high. Deep but rare; ignore it unless chasing a p99 spike.
Tooling map
  • py-spy (Python). Attaches to an already-running process, live, without restarting it: py-spy record -o profile.svg --pid 12345 --duration 30.
  • scalene (Python). Line-level CPU plus memory attribution.
  • Chrome DevTools / clinic (Node), pprof (Go), cargo-flamegraph (Rust), perf (C/C++). One go-to profiler per language.
  • The N+1 query. 1 query for the list, then 1 per row: 51 round trips instead of 1 JOIN. Invisible in the UI, obvious in the SQL log; fixed with eager loading (select_related, includes, selectinload, JOIN FETCH).
USE and RED: two checklists for "something's slow, but why?"
  • USE, for the machine underneath. For each resource (CPU, memory, disk, network): Utilization (how busy), Saturation (is work queueing), Errors (is it failing). First resource that trips one of the three is the bottleneck.
  • RED, for my own service. Rate (requests/s), Errors (failures/s), Duration (p50/p95/p99, never just the average; averages hide the slow outliers).

Profile and Fix (Voxa + ESLint)

Done
Two halves. Own code (the brief's fallback option): Voxa's test suite, 33-36s → 23.7s (PR #2). Someone else's repo (the task headline): ESLint + eslint-plugin-react-hooks, the plugin eats 30.7% of lint CPU while TIMING reports <1ms; findings posted as a data comment on facebook/react#35395 after the duplicate search found the issue already open.
What I did
Hypothesis first: I assumed the suite was CPU-bound in the websocket/audio paths. The first measurement killed that: 33s wall but only ~40% CPU, so the suite was mostly waiting. --durations showed the top 25 tests (2% of 1181) holding ~22s. Two wait sinks, both proven with a debugger rather than guessed. First: every websocket test's first connection ran real terminal discovery, osascript Apple Events to iTerm and Terminal.app plus tmux shell-outs, ~3.3s cold, and a TTL cache hid it from every later test, so the cost masqueraded as one "slow test" and sent me chasing a voice-param red herring. Second: six interrupt tests slept through the real 2×0.7s anti-double-esc retry gap, 7s total. Fixes: an autouse fixture stubbing discovery in test_app.py (one helper in the file already did exactly this locally, so the pattern was endorsed), and the 0.7s gap extracted to a class attribute (_interrupt_gap, production default unchanged) that those six tests set to 0. Remaining lead, journaled honestly: two hook tests cost ~3.1s in a full run but 0.8s in isolation, a cross-test contention effect not yet diagnosed. Committed locally on branch perf/faster-test-suite, not pushed, per this week's instruction.
before / after
$ time .venv/bin/python -m pytest tests -q
1180 passed, 1 skipped in 32.84s     # ~40% CPU: the suite is waiting
$ .venv/bin/python -m pytest tests -q --durations=25
3.34s test_voice_param_reaches_factory   # cold discovery, not voice
1.40s x5 interrupt tests                 # real 2x0.7s Escape gaps
$ time .venv/bin/python -m pytest tests -q   # after the two fixes
1180 passed, 1 skipped in 23.69s
The external half: ESLint + react-hooks v7
Since the task headline says someone else's repo, I also profiled a third-party tool from my real workflow: ESLint 9 with eslint-config-next on this site. All lint rules together cost ~2ms by ESLint's own TIMING=all accounting, yet the warm run burns 2.7s of CPU. The --cpu-prof capture answered it: eslint-plugin-react-hooks v7 (the React-Compiler-based rewrite) is the single largest consumer, 0.88s of 2.85s sampled (30.7%), more than @babel (11.8%) or typescript-eslint (10.1%), all in compiler passes like inferMutationAliasingRanges. The sharp part: TIMING attributes under 1ms to all react-hooks rules combined, so ESLint's only built-in perf diagnostic actively hides the biggest cost. Two more wrong hypotheses logged: "a misconfigured rule" (2ms total) and "the NODE_ENV development-build selection" (measured: ~3%). The duplicate search then earned its keep: facebook/react#35395 already reports the plugin dominating lint time, maintainers engaged, a perf fix already shipped. So instead of filing a duplicate, the findings went where they help: a comment on #35395 with the small-repo numbers and the angle the original lacked, that on 7.1.1 the cost has vanished from TIMING entirely.

Read 3 Real Flame Graphs

Done
Source: three published graphs from brendangregg.com, read from the raw SVG frame data (names, sample counts, widths), not just eyeballed.
Reading 1: Linux kernel TCP send
One tower stays ~99.8% wide from vfs_write all the way up through tcp_sendmsg, then narrows only gently: tcp_write_xmit 92.7%, ip_queue_xmit 89.3%, dev_queue_xmit 80.7%. There is no wide block at the top of the stack, so there is no hot leaf to optimize. The cost is smeared along the whole network stack: every packet pays the full traversal. The lever here is fewer, bigger sends (batching), not a faster function.
Reading 2: MySQL under a query load
dispatch_command (98%) funnels into JOIN::exec (78.3%), which splits into two towers: row fetching via InnoDB reverse index reads (~45.6% under do_select, with ha_innobase::index_prev at 24.4%) and create_sort_index/filesort at 31.2%. Read plainly: nearly a third of the server's entire CPU is sorting rows that the index did not deliver in order. That is the classic missing-or-wrong-index signature; the fix lives in the query or schema (an index satisfying the ORDER BY), not anywhere in mysqld's code.
Reading 3: bash running a while loop
78% of samples sit under execute_while_command. Inside it, execute_builtin_or_function is 44.7%, but do_redirections (24.9%) plus word expansion (20.6%) together match it: the shell spends about as much time setting up redirections and expanding words each iteration as it does running the actual builtins. That is the cost of a redirect inside a tight loop, re-opened every pass. Also instructive: 15.1% of samples are [unknown], missing symbols, the real-world annoyance every profiling guide warns about.
Definition of done
  • 3 real flame graphs found and linked. ✓
  • Journal reading per graph, in my own words: what's hot, what the bottleneck is, what I would do first. ✓

Use a Real Debugger

Done
Debugger: pdb (via pytest --trace)  ·  The bug: test_voice_param_reaches_factory took 3.34s while its nearly identical account twin took 0.2s. Zero print statements.
The session
Breakpoint at the wait call, c to hit it, stamp a timestamp from the pdb prompt, then n to step over the wait: 3 seconds elapse inside a single step. p captured shows the dict still empty, so the 300-poll wait loop exhausted without the value ever arriving; the assert only passes because the value lands during teardown. Then the move that cracked it: running faulthandler.dump_traceback() from the pdb prompt dumped every thread mid-hang. Two worker threads sat in subprocess.run inside discover_claude_sessions, one in _tty_of_tmux_panes (tmux) and one in discover_iterm (osascript Apple Events), while the event loop idled in select. The test was never slow because of the voice param: it was the first websocket connection of the run paying for real terminal discovery, which a TTL cache then hides from every later test. Confirmed by running the account twin alone: 3.77s. The delay lived on threads my print statements would never have executed on; the debugger saw them anyway.

Soft Skill, Intellectual Humility

Done
The principle: performance work is humbling. The senior move is trusting the measurement over the story. This week's score: three logged predictions, two wrong.
The wrong-predictions journal, week 8 entries
  • "The Voxa suite is CPU-bound." Wrong: 33s wall, ~40% CPU. It was 60% waiting on sleeps and subprocesses.
  • "The slow test is voice-param-specific." Wrong: the account twin alone took 3.77s. The cost was first-connection terminal discovery, and a TTL cache had been assigning the blame to whichever test connected first. The thread dump, not my theory, settled it.
  • "After the fix everything runs under a second." Wrong: two hook tests still cost ~3.1s in a full run but 0.8s in isolation, and I do not yet know why. That stays in the journal as an open item instead of a hand-wave.
The takeaway
The habit that did the work was stating each hypothesis before measuring and letting the tooling vote: durations first, then cProfile, then the pdb thread dump that overturned the story I had already half-written. Knowing versus assuming showed up concretely: "the factory sets the dict" was an assumption; p captured returning {} was knowledge.
