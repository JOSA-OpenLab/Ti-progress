The Standard

The unifying principle: the license is, legally, the single most important decision in an OSS project, and a public repo with no LICENSE file grants no rights at all. Visible on GitHub does not mean usable. This week is about choosing deliberately and setting up the foundations that make a project safe to invest time in.
The license question
  • Ask this first: do I care whether someone can take the code, modify it, and never share the changes back? No: permissive (MIT, Apache 2.0, BSD). Yes: copyleft (GPL, AGPL, MPL).
  • MIT for libraries meant for wide adoption; Apache 2.0 adds a patent grant and retaliation clause for non-trivial or enterprise-facing work.
  • GPL-3.0 keeps distributed derivatives open; AGPL-3.0 extends the trigger to use over a network, closing the SaaS loophole; MPL-2.0 is file-level copyleft, a pragmatic middle ground.
  • Beware source-available licenses (BSL, SSPL, Elastic, FSL): they read like OSS but are not OSI-approved. The tell is language singling out who can't use it commercially.
Community standards checklist
  • Copy-paste tier: LICENSE (named exactly that, not LICENSE.md), CODE_OF_CONDUCT.md (Contributor Covenant 2.1, don't write my own), issue/PR templates, CODEOWNERS.
  • Real-writing tier: README (name, badges, a 5-line example, one-line install, docs link; the example is the conversion event), CONTRIBUTING.md, SECURITY.md.
  • Versioning: SemVer with Keep a Changelog; below 1.0.0 is allowed to break. Conventional Commits let release-please or semantic-release cut releases automatically.
  • Governance: BDFL, do-ocracy, or committee. A new small project starts BDFL, but the decision process gets written down; implicit governance is the worst kind.

Pick the License

Done
Repo: Ti-03/MacDirStat  ·  License: AGPL-3.0, already in place, now justified deliberately instead of by momentum.
The justification
The copyleft question first: do I care if someone takes the code, modifies it, and never shares back? Yes. MacDirStat is a polished end-user app, and the realistic bad outcome is someone repackaging it as a paid app with private changes. AGPL's distribution trigger blocks exactly that, and its network trigger costs nothing here, since a local disk scanner has no SaaS story to lose. The twist that makes this repo's choice interesting: the same app ships on the Mac App Store (as DirStat), and GPL-family licenses are famously incompatible with App Store terms. That combination is legal for exactly one party, the copyright holder, who is not bound by their own license. So AGPL plus sole ownership works as de facto dual licensing: everyone else gets strong copyleft, the author keeps the store channel. The fine print: outside contributions would break sole ownership, so CONTRIBUTING.md now carries an explicit inbound-licensing clause (AGPL plus an App Store distribution grant). Also fixed the exact thing the brief warns about: the LICENSE file was the stock FSF text with no project copyright line, so the README gained Copyright © 2026 Qutibah Ananzeh and a License section explaining the choice.

Write the CONTRIBUTING.md

Done
Written as the document I wished every project had when I was the newcomer during weeks 4 through 8.
What it covers
Exact clone-to-run commands (swift run, zero dependencies), the one test command plus the CI-matrix gotcha that actually bites (runtime #available does not fix compile-time SDK breakage, the week 5 lesson, linked to its ADR), what makes a disk-scanner bug reproducible (macOS version, folder shape, network mounts and iCloud placeholders), issue-first PR conventions with the What/Why/How/Test structure, and honest review expectations from a solo maintainer: first response within a week, no one-on-one debugging support, narrow-use-case complexity gets a friendly no. Plus the clause this specific repo genuinely needs and template CONTRIBUTINGs never have: an inbound-licensing paragraph, because AGPL code that also ships on the App Store only works while the maintainer can license every line, so contributions carry an App Store distribution grant.
Definition of done
  • Setup, tests, bug filing, PR conventions, review expectations: all covered. ✓
  • A newcomer can go from clone to first PR without asking anything, including the licensing question they didn't know to ask. ✓
// 04

Document Governance

Done
One page, honest: BDFL, named, with the rules that used to live only in my head.
What it says
Decisions get reversed by better arguments and evidence, not volume. The feature bar is written down: serves the core job (see where your disk space went) without adding complexity everyone else pays for. Breaking changes require an ADR before they land. A no comes with a reason and an alternative, usually "fork it and I will link you from the README". And the document pre-commits to rewriting itself if a second maintainer ever earns commit access, because at two people "the founder decides" stops being governance and starts being a bottleneck. Twenty minutes of writing; the value is that the rules now exist somewhere other than my head.
Definition of done
  • GOVERNANCE.md, one page, honest BDFL. ✓
  • Decision process, merge rights, the shape of a no, and the path to shared maintainership. ✓

// 06

Soft Skill, Setting Boundaries (Saying No)

Done
The principle: maintainer burnout is the OSS occupational hazard, and the cause is almost always an inability to say no. Instead of rehearsing the three refusals in the abstract, they are now written into the project's actual documents, where they will get used.
Where each refusal now lives
  • The clear no with rationale lives in GOVERNANCE.md: every no comes with the reason and an alternative, usually "maintain it as a fork and I will link it from the README".
  • The not-now no lives in the feature bar: a good idea that is unstaffed gets "a PR that includes the maintenance (tests, docs) changes that answer".
  • The boundary no lives in CONTRIBUTING.md's review expectations: no one-on-one debugging support, a minimal reproducible example is the path to attention, first response within a week.
The takeaway
Boundaries are not rudeness; they are what keeps a maintainer alive in three years, and a project whose maintainer burned out serves nobody. Saying no kindly, in writing, before anyone asks, is cheaper than saying it badly, in an issue thread, at 1am.
