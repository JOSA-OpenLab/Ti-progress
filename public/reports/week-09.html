The Standard

The unifying principle: the license is, legally, the single most important decision in an OSS project, and a public repo with no LICENSE file grants no rights at all. Visible on GitHub does not mean usable. This week is about choosing deliberately and setting up the foundations that make a project safe to invest time in.
The license question
  • Ask this first: do I care whether someone can take the code, modify it, and never share the changes back? No: permissive (MIT, Apache 2.0, BSD). Yes: copyleft (GPL, AGPL, MPL).
  • MIT for libraries meant for wide adoption; Apache 2.0 adds a patent grant and retaliation clause for non-trivial or enterprise-facing work.
  • GPL-3.0 keeps distributed derivatives open; AGPL-3.0 extends the trigger to use over a network, closing the SaaS loophole; MPL-2.0 is file-level copyleft, a pragmatic middle ground.
  • Beware source-available licenses (BSL, SSPL, Elastic, FSL): they read like OSS but are not OSI-approved. The tell is language singling out who can't use it commercially.
Community standards checklist
  • Copy-paste tier: LICENSE (named exactly that, not LICENSE.md), CODE_OF_CONDUCT.md (Contributor Covenant 2.1, don't write my own), issue/PR templates, CODEOWNERS.
  • Real-writing tier: README (name, badges, a 5-line example, one-line install, docs link; the example is the conversion event), CONTRIBUTING.md, SECURITY.md.
  • Versioning: SemVer with Keep a Changelog; below 1.0.0 is allowed to break. Conventional Commits let release-please or semantic-release cut releases automatically.
  • Governance: BDFL, do-ocracy, or committee. A new small project starts BDFL, but the decision process gets written down; implicit governance is the worst kind.

Pending
Goal: cover setup, how to run tests, how to file a bug, PR conventions, and review expectations. This is what new contributors read first.
Plan
To do Write it as the document I wish every project had when I contributed during weeks 4 through 8: exact dev-environment setup commands, the one command that runs the tests, what a good bug report contains, commit/PR conventions, and what I promise as a reviewer (and how fast). Express's contributor docs are the quality bar.
Definition of done
  • CONTRIBUTING.md covers setup, tests, bug filing, PR conventions, review expectations.
  • A newcomer could go from clone to first PR without asking anything.
// 04

Document Governance

Pending
Goal: even as a solo BDFL, write a 1-page GOVERNANCE.md explaining how decisions are made.
Plan
To do State the model plainly: I (the founder) decide; if you disagree, file an issue and we discuss. Cover who merges, how disputes get resolved, and what would trigger moving to shared maintainership. The point is that implicit governance is the worst kind, so a page of honesty beats silence.
Definition of done
  • GOVERNANCE.md written, one page, honest about the BDFL model.
  • Documents the decision process, merge rights, and the path to shared maintainership.

// 06

Soft Skill, Setting Boundaries (Saying No)

Pending
The principle: maintainer burnout is the OSS occupational hazard, and the cause is almost always an inability to say no. An OSS project with bad boundaries dies with its maintainer; the kindest thing for future users is a maintainer who is still around in 3 years.
Three kind, firm refusals to practice
  • The clear no with rationale. "I've thought about this and decided not to, it adds API complexity for everyone to serve a smaller use case. If it matters to you, fork it and I'll link your fork from the README."
  • The not-now no. "Great idea, not on the roadmap for v1. I'd accept a PR if someone wants to maintain it as a plugin."
  • The boundary no. "I can't provide one-on-one debugging support. Post a minimal reproducible example as an issue and I'll look when I have time."
