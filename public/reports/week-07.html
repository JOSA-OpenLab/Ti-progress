The Standard

The unifying principle: most code in a modern app is not mine, an average npm app pulls in 1,000+ transitive dependencies, a Python web app 200+. Every one of those is an attack surface, and the goal this week is to use the free tooling that makes that surface visible instead of trusting it by default.
The supply chain in three layers
  • Dependency-on-itself. A package I depend on turns malicious: typosquatting, a maintainer going rogue, or a takeover like the xz/liblzma backdoor.
  • Build-process. CI itself is compromised, e.g. a GitHub Action imported as @main that silently changes underneath a project (the 2024 tj-actions/changed-files incident).
  • Distribution. A published artifact is tampered with after build. The defense is signing, Sigstore.
Tooling map
  • OpenSSF Scorecard. 18+ automated checks on any GitHub repo, 0-10 score: branch protection, code review, pinned dependencies, signed releases, SAST, token permissions.
  • Dependabot / Renovate. Bot-opened PRs for outdated deps. Default to Dependabot (zero-config); switch to Renovate for grouping or a polyglot repo.
  • Sigstore (cosign). Keyless signing tied to an existing GitHub/Google identity instead of managed GPG keys, logged to the public Rekor transparency log.
  • SBOM (Syft + Grype). A CycloneDX/SPDX inventory of every dependency, version, and license; Grype cross-references it against osv.dev for known CVEs.
Case study: the xz backdoor (CVE-2024-3094)
A contributor spent two years quietly building maintainer trust on the xz compression library, then landed a backdoor in liblzma that compromised SSH on most Linux distros. It was caught by accident, a Microsoft engineer noticed slow SSH logins. The lesson: a single-maintainer project is a single point of failure, tarball releases can differ from what is visible in git tags, and long-game social engineering is a real threat model. Scorecard, Sigstore, and SBOMs are built against exactly this failure mode.

Add Dependabot

Pending
Goal: configure Dependabot for one repo, both the code ecosystem and github-actions, pin every Action to a commit SHA, and submit as a PR.
Plan
To do Add .github/dependabot.yml with a weekly schedule for the repo's package ecosystem and for github-actions. Pinning to @v4 still exposes any vulnerability published under that tag, so every existing uses: line gets rewritten to a commit SHA with the version kept as a trailing comment.
.github/dependabot.yml
version: 2
updates:
  - package-ecosystem: npm
    directory: /
    schedule: { interval: weekly }
  - package-ecosystem: github-actions
    directory: /
    schedule: { interval: weekly }
Definition of done
  • .github/dependabot.yml covers both the language ecosystem and github-actions.
  • Every uses: line in the workflows is pinned by commit SHA, not a mutable tag.
  • Change submitted as a PR.

Sign a Release with Sigstore

Pending
Goal: tag a release, sign the artifact with cosign, and document the verify command in the README.
Plan
To do Sign the release artifact with cosign, authenticating keylessly against a GitHub identity, so the signature ties to the exact workflow and tag rather than a private key someone has to guard forever.
cosign sign-blob / verify-blob
$ cosign sign-blob --yes ./release.tar.gz --output-signature release.tar.gz.sig
$ cosign verify-blob \
    --certificate-identity '<workflow-url>@refs/tags/v1.0.0' \
    --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
    --signature release.tar.gz.sig ./release.tar.gz
Definition of done
  • Release tagged, artifact built.
  • Artifact signed with cosign, signature logged to Rekor.
  • Verify command documented in the README so anyone can check it.

Generate and Read an SBOM

Pending
Goal: run Syft on a project, run Grype against the SBOM, and write a journal entry on any known CVEs that surface.
Plan
To do Generate a CycloneDX SBOM with Syft, then feed it to Grype to check every listed package and version against osv.dev. If anything shows up, pick one finding and dig in: what the CVE actually affects, whether the fix is a version bump, and who else it touches.
syft + grype
$ syft ./my-app --output cyclonedx-json=sbom.json
$ grype sbom:sbom.json
Definition of done
  • sbom.json generated for a real project.
  • Grype run against it, output captured.
  • Journal entry written on the findings, with one CVE investigated in depth.

Run OpenSSF Scorecard

Pending
Goal: run Scorecard on a project, then try to open a PR fixing the lowest-scoring check.
Plan
To do Run Scorecard against one of my own repos, read through the 18+ checks, and treat the lowest score as the actual target instead of chasing every checkbox. Per the soft-skill note this week, not every check matters equally: branch protection on main is worth fighting for, pinned dependencies on a hobby repo is not.
scorecard
$ go install github.com/ossf/scorecard/v5/cmd/scorecard@latest
$ scorecard --repo=github.com/<owner>/<repo>
Definition of done
  • Scorecard run, full report read, lowest-scoring check identified.
  • PR opened addressing that specific check.

Soft Skill, Conscientious Skepticism

Pending
The principle: security work needs someone who asks "but what if this fails?" without becoming the person nobody invites back to the kickoff meeting.
Specific moves to practice this week
  • Phrase concerns as questions. "What's the threat model for this dependency?" lands differently than "we can't add this".
  • Bring data, not alarm. "3 known CVEs in the last year and a Scorecard of 4/10, here's the alternative" beats "this is risky".
  • Pick battles. Branch protection on main is a real fight; Pinned-Dependencies on a hobby project is not.
  • Default to charity. A sketchy dependency usually means someone was trying to ship, not being careless. Educate, don't blame.
