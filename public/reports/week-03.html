Reproduce One Issue

Goal: Find an active issue in one of the suggested repos, reproduce it on your machine, and post a comment with your environment, the steps you ran, and the actual outcome.
Issue Reproduced

Repo: httpie/cli  ·  Issue #1640 →  ·  My comment →

Bug: Content-Type: application/json is dropped from a POST when exactly one custom header is present alongside JSON data items.

Environment

macOS (Darwin 25.5.0), Apple Silicon  ·  HTTPie 3.2.4  ·  Requests 2.34.2  ·  Python 3.13.13  ·  isolated uv venv — the only variable changed between runs was multidict.

Steps & Outcome

A fresh install didn't reproduce — the clue that the bug lived in a dependency, not in httpie. Pinning the yanked multidict==6.5.0 isolated the exact trigger.

bash 
# Isolated env, then pin the yanked/buggy dependency
uv venv httpie-repro && source httpie-repro/bin/activate && uv pip install httpie
uv pip install 'multidict==6.5.0'

# One header -> Content-Type MISSING (bug)
http --print=H --ignore-stdin post pie.dev/post 'header1: xyz' x=1

# Two headers -> Content-Type present (works)
http --print=H --ignore-stdin post pie.dev/post 'header1: xyz' 'header2: abc' x=1

# Upgrade the dependency -> 6.7.1, single-header case fixed
uv pip install -U multidict
result 
Boundary under multidict 6.5.0 — is Content-Type: application/json present?
  0 headers: PRESENT
  1 header:  MISSING   <- bug
  2 headers: PRESENT
  3 headers: PRESENT

# pie.dev echoed back no Content-Type for the 1-header request,
# confirming it was genuinely not sent (not a display quirk).
# After upgrading multidict to 6.7.1: 1-header case PRESENT (fixed).
Reflection
A fresh install couldn't reproduce the bug — and that "can't reproduce" was itself the finding. The only difference between my machine and the reporter's was a single transitive dependency: multidict. Pinning the yanked 6.5.0 in an isolated venv and changing nothing else proved the root cause, and the boundary turned out to be exact — only a single custom header drops Content-Type, while 0, 2, and 3 keep it. I confirmed the request was genuinely sent without the header by checking what pie.dev echoed back, rather than trusting HTTPie's own display. The lesson: when a bug won't reproduce on a clean install, suspect the dependency tree before the project's own code.

Build One MCVE

Goal: Take an issue with a sprawling reproduction and reduce it to the smallest possible code that still triggers the failure — Minimum, Complete, Verifiable Example.
Issue

Repo: httpie/cli  ·  Issue #1640 →  ·  MCVE comment →

Reduced from: a uv venv + httpie install + a live POST to pie.dev  →  to: 3 lines of pure Python, only multidict, no network.

MCVE
python 
# Fails (exit 1) on multidict==6.5.0; passes (exit 0) on 6.5.1+
from multidict import CIMultiDict

md = CIMultiDict({"a":"1","b":"2","c":"3","d":"4","e":"5"})
md.popone("a")            # remove the first key
md.update([("a","1")])    # add it back

assert set(md.keys()) == {"a","b","c","d","e"}  # drops a key on 6.5.0

Minimum: exactly 5 keys (4 and 6 don't trigger it — it's a hash-table internals bug). Complete: only needs multidict. Verifiable: self-checking assert + exit code. Matches the upstream regression test in aio-libs/multidict#1196.

Reflection
I reduced the sprawling #1640 reproduction (a venv, an httpie install, and a live network call) to three lines of pure Python that need only multidict. The path was mechanical: trace httpie's apply_missing_repeated_headers() to the operation it relies on — popone() then update() — reproduce that directly on a CIMultiDict, then minimize the input. The minimization was the interesting part: exactly 5 keys triggers it while 4 and 6 don't, which told me this is a hash-table internals bug, not a logic error. Making it self-verifying with an assert and an exit code means it doubles as a bisect/CI probe. The lesson: a good MCVE deletes everything that isn't the bug — here that meant removing httpie and the network entirely and landing on the single multidict call that actually fails.

Run a Bisect

Goal: Find a behavior that changed between versions and use git bisect to identify the exact commit that introduced the change — in O(log n) steps.
Project & Behavior

Repo: aio-libs/multidict  ·  the dependency behind httpie/cli#1640 from Tasks 1&2.

What changed: the Task 2 MCVE (a popone() then update() on a 5-key CIMultiDict) silently drops a key. The version window is exact — 6.4.4 works, 6.5.0 breaks, 6.5.1 works again — so the regression lived in exactly one release, which is why 6.5.0 was yanked from PyPI.

Twist: the bug only exists in multidict's compiled C extension. With MULTIDICT_NO_EXTENSIONS=1 the pure-Python fallback is correct on every version — so there was no Python line to bisect, and every step had to rebuild the extension.

Bisect Session

A git bisect run script builds the C extension in place and runs the MCVE, returning 0=good / 1=bad (and 125 to skip any commit that won't compile). 7 commits in the window resolved in 3 automated builds — O(log n).

bash 
# probe builds the C ext, then runs Task 2's 5-key MCVE (exit 0/1, 125=skip)
git clone https://github.com/aio-libs/multidict.git && cd multidict
git bisect start v6.5.0 v6.4.4   # bad = 6.5.0 (yanked), good = 6.4.4
git bisect run bash bisect_test.sh
git bisect reset
result 
Reproducer signal (C extension):  6.4.4 GOOD | 6.5.0 BAD | 6.5.1 GOOD
(pure-Python fallback is GOOD on every version)

Bisecting v6.4.4..v6.5.0 — 7 commits, ~3 steps:
  good  87c76b8  Fix failed spelling task (#1168)
  good  bdbbc48  Bump pytest-cov from 6.0.0 to 6.1.0 (#1119)
  bad   9d3c53f  Replace pair_list with hash table (#1128)  <- first bad
Culprit Commit

9d3c53f — "Replace pair_list with hash table (#1128)" →  ·  Andrew Svetlov, 2025-06-17  ·  parent bdbbc48 confirmed good.

This commit swapped multidict's internal storage from a linked pair-list to a CPython-dict-style hash table for O(1) lookups. The new tombstone/index bookkeeping mishandled the delete-then-reinsert pattern (popone then update), dropping a sibling key. Severe enough to yank 6.5.0; fixed in 6.5.1.

Reflection
I bisected the exact commit behind the same bug as Tasks 1 and 2, feeding the bisect my 5-key MCVE as the good/bad probe. Two things made it more than a mechanical run. First, the bug lives only in multidict's compiled C extension — with MULTIDICT_NO_EXTENSIONS=1 every version is correct — so there was no Python line to bisect and each step had to rebuild the extension, with the script returning 125 to skip uncompilable commits. Second, the window was unusually sharp: the regression existed in exactly one release. Bisecting 7 commits took 3 automated builds and landed on 9d3c53f, the rewrite of multidict's internal storage from a pair-list to a hash table. The lesson: "which version broke it" and "which commit broke it" are different questions — git bisect run answers the second mechanically, but only once you have a reproducer that emits a clean good/bad signal, and here that first meant discovering the bug was in C, not Python.

Triage an Issue

Goal: Pick a stale or unconfirmed issue and triage it — confirm, duplicate, close, or ask for more info. Submit a journal entry summarizing what you found.
Issue Triaged

Repo: t3-oss/create-t3-app  ·  Issue #2215 →  ·  My triage comment →

Bug: the --import-alias flag crashes with TypeError: i.replace is not a function when used in CI mode. A different repo from #1640 — chosen for breadth.

Triage Action

Confirmed on the current npm latest (create-t3-app@7.40.0) — ran it twice and read the released dist — with environment, steps, outcome, a precise root cause, and a polite correction to the original analysis.

result 
# Confirmed: create-t3-app@7.40.0 · Node 26.0.0 · npm 11.12.1 · macOS (Darwin 25.5.0)
npx create-t3-app@7.40.0 my-app --CI --tailwind --appRouter --eslint --import-alias "@/"
-> scaffolds, then crashes: TypeError: i.replace is not a function

# Root cause in the RELEASED build:
.option('-i, --import-alias', '...', '~/')   # registered as a BOOLEAN — no [alias] placeholder
  -> Commander discards "@/" and sets importAlias = true
  -> guard `if (importAlias !== '~/')` passes  (true !== '~/')
  -> setImportAlias() calls .replace() on a boolean -> crash

Correction issued: the original analysis assumed an optional [alias] resolving to true — but the released build has no value placeholder at all, so the flag never accepts a value. The current main source does use -i, --import-alias [alias], which wouldn't crash, but that isn't in 7.40.0.

Reflection
I triaged an unconfirmed bug in a different repo for breadth, and the key discipline was triaging the artifact the reporter actually ran — the published 7.40.0 dist — not the repo's HEAD. The two had diverged: main registers the flag as -i, --import-alias [alias] (which accepts a value and wouldn't crash), while the released build registers it as a plain boolean with no value placeholder, so Commander sets importAlias = true and setImportAlias() later calls .replace() on a boolean. Reading HEAD alone would have produced a wrong "cannot reproduce." I confirmed it, gave a precise root cause, and politely corrected the original analysis rather than just agreeing with it. The lesson: a confirmation is only as trustworthy as the build you ran it against.
