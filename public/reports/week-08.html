The Standard

The unifying principle: don't optimize on gut feeling. Measure first, fix what actually costs the most (how often it runs times how slow it is), then measure again. Knuth's 97% of code doesn't matter for speed; the whole week is about finding the 3% that does.
Reading a flame graph
  • Width = CPU time, height = call depth. The x-axis is not time; it is how often a function showed up while the profiler sampled.
  • Wide block at the top of a stack. The function actually doing the work. Prime suspect, optimize it directly.
  • Stack stays wide then suddenly narrows. The time went where the width drops, not at the top of the stack.
  • Skinny sliver going way up high. Deep but rare; ignore it unless chasing a p99 spike.
Tooling map
  • py-spy (Python). Attaches to an already-running process, live, without restarting it: py-spy record -o profile.svg --pid 12345 --duration 30.
  • scalene (Python). Line-level CPU plus memory attribution.
  • Chrome DevTools / clinic (Node), pprof (Go), cargo-flamegraph (Rust), perf (C/C++). One go-to profiler per language.
  • The N+1 query. 1 query for the list, then 1 per row: 51 round trips instead of 1 JOIN. Invisible in the UI, obvious in the SQL log; fixed with eager loading (select_related, includes, selectinload, JOIN FETCH).
USE and RED: two checklists for "something's slow, but why?"
  • USE, for the machine underneath. For each resource (CPU, memory, disk, network): Utilization (how busy), Saturation (is work queueing), Errors (is it failing). First resource that trips one of the three is the bottleneck.
  • RED, for my own service. Rate (requests/s), Errors (failures/s), Duration (p50/p95/p99, never just the average; averages hide the slow outliers).

Profile and Fix (Someone Else's Repo)

Pending
Goal: profile a real workflow in an open-source project I actually use, find a function taking >50ms with a flame graph, and open a PR if a small safe fix exists. Either way, open an issue with the flame graph, the specific function, and the numbers.
Plan
To do Pick a library or CLI tool from my daily stack and profile a real workload: its test suite, a heavy command, or a script that uses it. State a hypothesis first ("I think the bottleneck is X"), then let the flame graph confirm or embarrass it. Findings get filed as an issue with numbers in the shape "840ms for 10k items, function X is 91% of that time", and the before/after goes in my journal whether or not the maintainers respond.
py-spy
# attach to a live process and record 30s as a flame graph
$ py-spy record -o profile.svg --pid 12345 --duration 30
# or profile a workload from the start
$ py-spy record -o profile.svg -- python -m pytest tests/
Definition of done
  • Real workflow profiled, flame graph produced.
  • A >50ms function identified as the bottleneck, with numbers.
  • Issue opened with the flame graph attached; PR opened if a small safe fix exists.
  • Before/after documented in the journal.

Find an N+1 Query (Bonus)

Pending
Goal: turn on SQL logging in an open-source web app and browse for a page issuing N+1 queries. Bonus task: not finding one is a valid outcome, noted in the journal.
Plan
To do Run an OSS web app locally with SQL logging on and click through list-heavy pages (dashboards, feeds, tables with per-row relations). The tell is the same query shape repeating dozens of times with only the id changing. If one shows up: issue with the query log as evidence, plus a PR if the fix is a one-line eager load. If not, journal the attempt and move on.
Definition of done
  • SQL logging enabled on a real OSS web app, several pages exercised.
  • If an N+1 is found: issue opened with the query log, PR if the fix is small and obvious.
  • If not found: journal entry noting what was checked.

Use a Real Debugger

Pending
Goal: pick the debugger for my primary language and solve one bug end-to-end with breakpoints. No print statements.
Plan
To do Take a real bug and work it entirely inside the debugger: breakpoint at the suspected site, inspect state, step through, watch the moment the data goes wrong. The discipline is separating what I know from what I assume; every unchecked assumption is where the bug hides. Document the session and how it compares to print-debugging.
lldb
$ lldb ./my-binary
(lldb) b suspicious_function
(lldb) run
(lldb) p state_variable
(lldb) next / step / continue
Definition of done
  • One bug solved end-to-end with breakpoints, zero print statements.
  • Debugger session documented: breakpoints set, state inspected, the moment the bug revealed itself.

Soft Skill, Intellectual Humility

Pending
The principle: performance work is humbling. Code I thought was fast will be slow; code I wrote off as "probably fine" will dominate the profile. The senior move is trusting the measurement over the story.
Three habits to practice this week
  • State a hypothesis before measuring. "I think the bottleneck is the database call." Then measure, and notice when wrong. Calibration compounds over months.
  • When wrong, say so out loud. "I thought X but the data shows Y." Admitting error in public is the most credible form of leadership.
  • Keep a wrong-predictions journal. One line per confident-but-wrong call; reread monthly to spot where my gut systematically fails.
